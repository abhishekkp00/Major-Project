# SecureLoRA Jury Demo Runbook

This runbook is designed for a short, repeatable demonstration. Use only synthetic/sample data and the values returned by the running application.

## Before the presentation

1. Start the application using the repository's documented setup instructions.
2. Open the Workbench and confirm that the dataset templates load from the backend.
3. Select a small synthetic dataset and verify that the launch button is enabled.
4. Run one complete pipeline before the jury arrives. Record the run ID and confirm the terminal/server logs contain no unhandled exceptions.
5. Open **Metrics** and confirm the run appears in the selector. Live run values and historical research artifacts must be identified separately.
6. Open **Security** and verify the available test actions against the backend. Do not describe a test as successful unless its returned result says so.
7. Keep a terminal visible nearby so failures can be diagnosed without pretending the run succeeded.

## Suggested 5–7 minute sequence

### 1. State the problem (30 seconds)

LoRA adapters are lightweight to distribute, but the fine-tuning and deployment lifecycle can still expose personal data, weaken privacy, or accept an untrusted or unauthorized adapter. SecureLoRA brings privacy controls, adapter screening, package integrity, and device-bound deployment checks into one workflow.

### 2. Run the pipeline (2–3 minutes)

- Select a **synthetic** dataset and a small subset appropriate for the machine.
- Explain the configured training mode before launching.
- Start the pipeline and show the actual stage/progress updates.
- Point out the run ID and the completed/failed state.
- Do not quote an expected runtime until it has been measured on the presentation machine.

### 3. Explain the evidence (1 minute)

- Show the executed run in **Metrics** first.
- Explain which values came from that run and which values are unavailable.
- Select historical research artifacts only when explicitly discussing those experiments. They are not results from the current live run.
- For DP-LoRA, distinguish the configured target epsilon and noise multiplier from the epsilon actually computed by the privacy accountant. A configuration field alone is not proof of a privacy guarantee.

### 4. Demonstrate deployment defenses (1–2 minutes)

Use the **Security** actions one at a time:
1. Tamper with a package.
2. Attempt deployment from a wrong device.
3. Attempt a replay.
4. If the suspicious-adapter test is available, explain that it exercises the screening path.

For each action, show the backend response and identify the gate that rejected or accepted it. A single test demonstrates that scenario, not universal security.

### 5. Close with limitations and next steps (30 seconds)

Summarize what is implemented, what evidence was generated during the demo, and what remains research-only. Be explicit that a software-derived device fingerprint is not equivalent to a TPM-backed hardware root of trust.

## Evidence and claim discipline

- **Live run:** results tied to the selected run ID and returned by the running backend.
- **Historical artifact:** a saved result under `outputs/evaluation/`; it must not be described as generated by the current run.
- **Not executed / unavailable:** show as unavailable rather than estimating, copying, or inventing a value.
- **Behavioral screening:** the current packaging orchestrator documents that it has no live model-inference callback and therefore invokes screening in research mode with synthetic baseline responses. Do not claim that this path performed real candidate-model behavioral inference. The report's provenance fields should be included when discussing screening.
- **Privacy:** a configured DP parameter is not itself a measured epsilon. Report the accountant output, delta, clipping/noise settings, and dataset/training context together.
- **Secure deletion:** temporary-file cleanup attempts do not prove physical erasure on every filesystem or storage device.
- **Device binding:** software-derived fingerprints can be spoofed or changed and should not be described as hardware-rooted attestation.

## If something fails live

1. Stop and read the inline error plus server logs.
2. Do not switch to historical charts without explicitly changing the selector and naming them as historical.
3. If training is slow, explain the machine and dataset-size constraints; do not present a partial run as completed.
4. If a security action fails to execute, say that the test could not be completed and show the code path or a previously saved test result with its provenance clearly stated.
